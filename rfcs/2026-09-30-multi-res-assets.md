# RFC：多倍图资源适配

- **状态**：已接受
- **日期**：2026-09-30
- **作者**：末语项目组
- **适用范围**：`moyu`（引擎 Rust 侧）、`moyu-docs`；`@momoyu-ink/cli` 无需改动
- **相关实现**：`crates/platform/src/config.rs`（`MoyuConfig`）、`crates/core/src/core.rs`（`Core::new` / `resize_stage`）、`crates/core/src/base/mvp_matrix.rs`（`get_scale_and_translate`）、`crates/resource/src/lib.rs`（`load_asset`）、`crates/resource/src/loaders/texture.rs`、`crates/nodes/src/renderer/sprite.rs`、`crates/nodes/src/renderer/animation.rs`、`crates/platform/src/fs/read.rs`
- **相关 RFC**：无

## 摘要

本文为末语引擎引入**多倍图资源适配**：同一逻辑资源可以有多个像素倍的变体文件，用 `@<数值>x` 后缀区分，例如 `abc.png` 与 `abc@2x.png`、`abc@1.5x.png`。

引擎在加载纹理类资源时，按**当前物理像素与舞台单位的倍率**自动选择最合适的变体，项目侧只需引用基础名（`abc.png`），不需要在引用处声明任何东西。功能由 `index.json` 控制，**默认关闭**。

引擎没有目录列举能力，因此变体是否存在只能靠**试读**得到；这决定了**要试哪些档位必须是已知的**，即一个明确的候选档位集合。该集合有内置默认值（`[1.5, 2]`），项目可用一行配置整体覆盖。

默认关闭是考虑到试读在 web 上会转化为额外的 HTTP 请求：不开启时请求数与现在完全一致，作者按需开启。开启后仍有一条零试读路径：显示倍率不高于 1（1080p 窗口、移动端横屏等常见情况）时基础图就是第一个候选，不发出任何变体请求。

## 背景

### 现状

- 舞台尺寸由 `index.json` 的 `stageSize` 固定，是一个逻辑尺寸；渲染时舞台被等比 fit 到 surface（`get_scale_and_translate`，取 `min(宽比, 高比)`），再乘以 dpr 映射到物理像素（`MVPMatrix::from_logical_size`）。
- 资源读取路径：`load_asset(kind, src)`（`crates/resource/src/lib.rs`）把 `src` 拼到 `assets_dir()` 上得到 URL，作为 `AssetId` 的 key，异步读取并上传纹理；动画节点则在 `crates/nodes/src/renderer/animation.rs` 里直接 `fs::read` 字节，自行解码。
- 纹理的像素尺寸被直接当作舞台单位使用：sprite 的 `local_bounds` 由 `tex_width/tex_height × area` 计算（`calculate_sprite_instance`），`prepare` 里把同样的值写进 `intrinsic_size`；animation 的顶点尺寸与 `intrinsic_size` 同样来自帧的像素尺寸。
- 引擎没有任何资源清单或目录列举能力。平台层只有 `readdir_from_appdata`（存档 / 设置用），assets 目录既没有列举 API 也没有清单：web 走 HTTP GET，Android 走 `AssetManager.open`（未使用 `AssetManager.list`），desktop 走文件路径，都只能"按已知路径读取"。
- **开发期在所有平台上 assets 都经 HTTP 读取**：`moyu run` 用 `--entry http://localhost:6020/index.json` 启动引擎（`packages/cli/src/commands/run.ts`），web 模式经 CLI 的静态服务器，native 模式直接吃打包器 dev server 的输出。也就是说"能列目录"这条路在开发期根本不存在，只有打包后的 native / Android / iOS 上才有。
- 舞台尺寸与窗口尺寸的关系目前对资源加载完全不可见——加载逻辑不知道当前画面上一个舞台单位对应几个物理像素。

### 现状不足

高分屏（4K 全屏、1440p、HiDPI 笔记本）上，1920×1080 的舞台被放大 1.3～2 倍显示，素材被拉伸导致模糊。项目目前只能二选一：全部素材按 2 倍制作（在 1080p 上浪费显存与包体），或者接受模糊。

## 目标

本文规定：

- 变体文件的命名约定与合法数值；
- "显示倍率"的计算方式；
- 候选档位集合的定义、默认值与覆盖方式；
- 档位匹配策略与默认行为；
- 变体文件的试读方式、缓存策略与开销上限；
- 像素倍率如何传递到渲染，保证切换变体不改变画面尺寸；
- `index.json` 的开关设计；
- 与编辑器、打包、测试的关系及跨仓影响。

## 非目标

- **不**为音频、视频、字体做多倍图（前两者按内容选档，字体是矢量）。
- **不**在窗口尺寸变化时热切换已加载的素材（见"已知取舍"）。
- **不**自动处理"素材被节点放大"的情况（例如 1280 宽的背景铺满 1920 舞台）：引擎只看舞台与 surface 的倍率，不参与节点级缩放与相机变焦。
- **不**引入资源清单 / 构建期索引（列为后续优化）：引擎只按已知候选档位试读，不扫描目录。
- **不**把变体机制当作平台差异化打包手段（移动端省包体应通过打包裁剪而不是多倍图）。
- **不**改变 `readFile('assets:...')`、调试桥、`insert_asset`（内置资源）的行为。

## 术语

### 基础图（base asset）

项目引用的名字，不带 `@Nx` 后缀，约定为 1 倍图，例如 `bg/room.png`。基础图必须存在（与现在一致）。

### 变体（variant）

与基础图同目录、同扩展名，文件名主体带 `@<数值>x` 后缀的文件，例如 `bg/room@2x.png`。

### 档位（scale）

变体后缀里的数值，表示该文件的像素倍率。基础图等价于档位 `1`。

### 候选档位集合（candidate scales）

引擎在一次加载中**允许尝试**的档位列表，由 `index.json` 的 `multiResAssetScales` 配置，有内置默认值。基础图（档位 `1`）隐式始终属于候选集合，且不需要试读。

集合之外的文件即使存在也不会被自动匹配——这是"引擎无法列举目录"的直接后果，也是本设计最重要的使用约束。列表里不能出现 `1`（基础图已隐式包含），也不能出现非正数。

### 试读（probe）

一次"按候选路径读取文件"的尝试。读取失败、或读取成功但无法解码为图片，都视为该候选不存在。

### 显示倍率（ratio，记作 T）

当前一个舞台单位对应多少物理像素，由 surface 物理尺寸与舞台尺寸决定：

```
T = min(surface_physical_width / stage_width, surface_physical_height / stage_height)
```

取 `min` 而不是 `max`，因为舞台是等比 fit 进 surface 的，letterbox 黑边不需要更高像素的素材。用物理像素而非逻辑尺寸是必须的：4K 屏 + dpr 2 + 逻辑窗口 1920×1080 时物理尺寸仍是 3840×2160，`T = 2`，与 dpr 1 的 4K 屏一致。

| 场景 | 物理分辨率 | 舞台 | T |
| --- | --- | --- | --- |
| 4K 全屏 | 3840×2160 | 1920×1080 | 2.00 |
| 4K 屏 dpr 2，逻辑窗口 1920×1080 | 3840×2160 | 同上 | 2.00 |
| 1440p 全屏 | 2560×1440 | 同上 | 1.33 |
| 1280×720 窗口 | 1280×720 | 同上 | 0.67 |
| 手机横屏 2400×1080（dpr 2.75） | 2400×1080 | 同上 | 1.00 |

### 像素倍率（pixel ratio）

某个**文件**本身的倍率。基础图与 `@1x` 为 1，`abc@2x.png` 为 2。引擎用它把文件像素尺寸换算成舞台单位：`逻辑尺寸 = 像素尺寸 / pixelRatio`。

## 总体设计

### 命名约定

变体名称为：`<主体>@<数值>x.<扩展名>`，`@<数值>x` 插在**最后一个点之前**，作用在文件名（不含目录）上。

- 数值为正数，支持小数：`@2x`、`@1.5x`、`@1.33x`、`@0.5x`；后缀里的 `x` 大小写不敏感。
- 命名本身不受限制，但**只有候选档位集合里的数值能被自动匹配**。集合外的高倍图（例如 `@1.33x` 而集合为默认值）不会被使用，也不会报错。要使用集合外的档位只有两条路：写进 `multiResAssetScales`，或显式引用完整文件名（见下条，代价是该处固定为该档）。编辑器应对"文件存在但不会被自动使用"的情况给出警告。
- 不接受 `@0x`、负数、非数字、`@1.5.5x`。这类名字按普通文件名处理（不报错）。
- `@1x` 文件不参与自动匹配（档位 `1` 等于基础图，且基础图必须存在），创建它没有意义。
- **带 `@<数值>x` 的文件名是"精确引用"**：引用 `abc@2x.png` 时引擎不再寻找其它变体，并按其 pixelRatio 处理（逻辑尺寸 = 像素尺寸 / 2）。这与 iOS `UIImage.scale` 语义一致，也提供了一个强制指定档位的逃生口。注意这意味着项目直接引用变体文件时，画面尺寸与引用基础图相同——如果这不是预期，说明作者误解了该约定，编辑器应通过隐藏变体文件来避免。

自动匹配部分只处理**基础名**（`abc.png`）；变体的查找只发生在同一目录、同一扩展名内。

### 档位匹配

候选集合 = `{1} ∪ multiResAssetScales`，按策略排序成候选顺序，逐个试读，命中即停。

匹配策略由 `multiResAssetPolicy` 决定，默认 `quality`：

- `quality`（清晰度优先）：`[档位 ≥ T 的升序]` ++ `[档位 < T 的降序]`。即优先取"≥ T 的最小档"，该档缺失时逐级向下回退，最终落到基础图；只要变体存在就不会把素材放大。
- `balanced`（显存优先）：按 `|ln(档位 / T)|` 升序，同距离时取较大档。占用更小，但 HiDPI 下可能仍使用基础图。

以默认集合 `{1, 1.5, 2}` 为例：

| T | `quality`（默认）候选顺序 | 实际使用（有变体时） |
| --- | --- | --- |
| 2.00（4K） | 2, 1.5, 1 | 2 |
| 1.33（1440p） | 1.5, 2, 1 | 1.5 |
| 1.10 | 1.5, 2, 1 | 1.5 |
| 0.67（720p 窗口） | 1, 1.5, 2 | 1（零试读） |
| 0.40 | 1, 1.5, 2 | 1（零试读） |

基础图在候选顺序里的位置决定了试读次数：

- `T ≤ 1` 时基础图排在首位 → **零试读**。覆盖 1080p 窗口、手机横屏（T ≈ 1）等绝大多数场景。
- `T > 1` 时先试变体，全部缺失才回退基础图 → 每个资源最多 `|multiResAssetScales|` 次失败试读。

### 试读与缓存

前提（见"现状"）：引擎**无法列举 `assets/`**，开发期所有平台都经 HTTP 读取。因此变体存在性只能靠试读，且必须按**已知的**档位去试——这就是候选档位集合必须显式给出（或取默认值）的原因。

- **候选顺序**：`{1} ∪ multiResAssetScales` 按策略排序（见上节）。档位 `1` 直接映射到基础图 URL，无须试读。
- **试读与加载合并为一次读取**：`resolve_variant(src)` 在同一个异步任务里按候选顺序读取，命中即返回 `(实际 URL, pixel_ratio, 字节)`，避免"先探测再读取"读两遍。
- **失败判定**：读取失败（404 / 文件不存在），或读取成功但解码失败，都视为该候选不存在。后者是必需的——`moyu run` 的静态服务器在分层查找 miss 后会代理到打包器 dev server（`packages/cli/src/utils/static-server.ts`），未知路径可能返回 200 + HTML。
- **缓存（按逻辑资源）**：`逻辑 src → (实际 URL, pixel_ratio)`，或 `无可用变体`。同一资源的重复加载不再试读。
- **日志**：试读 miss 记 `debug!`；命中变体记 `debug!`（`abc.png → abc@2x.png（档位 2）`）。只有**全部候选（含基础图）都读不到**时才按现有行为记 `error!`。

不做"某档位全局失败后跳过"这类跨资源缓存：单个资源是否有多倍图是**独立事实**，用全局统计推断会漏检（例如只有背景有 `@2x`、UI 素材没有，先加载的 UI 会把 `@2x` 判定为不可用，背景于是降级到基础图）。代价是开销与资源数成正比，见下表。

开销（假设已启用，默认集合 `{1, 1.5, 2}`，每资源一次试读上限）：

| 场景 | 额外请求 | 说明 |
| --- | --- | --- |
| 默认（`multiResAssets: "off"`） | **0** | 与现在完全一致 |
| 启用 `auto`，`T ≤ 1`（1080p 窗口、手机横屏） | **0** | 基础图是第一个候选 |
| 启用 `auto`，`T > 1`，项目有变体 | 每资源 1 次 | 通常第一个候选即命中 |
| 启用 `auto`，`T > 1`，项目无变体 | 每资源 ≤ 2 次 | 全部候选失败后回退到基础图 |
| `multiResAssetScales: []` | **0** | 只保留基础图，无需关闭总开关 |

试读是只读探测，不产生解码与上传开销；失败请求在 keep-alive 与静态服务器上是低成本操作。集合里声明了但实际不存在的档位（例如集合含 `3` 而项目只做了 `@2x`）会让每个资源多一次失败试读——这也是默认集合只放两个最常见档位的原因。

### 像素倍率的传递

切换变体不能改变画面尺寸，凡是"把纹理像素当舞台单位用"的地方都要除以 pixelRatio：

1. `crates/resource`：`Texture` 增加 `pixel_ratio`（默认 1），由加载器在解析出实际文件后写入。
2. `crates/nodes/src/renderer/sprite.rs`：`prepare` 中写入 `intrinsic_size` 的尺寸、`update` 中 `calculate_sprite_instance` 的 `tex_width/tex_height`（九宫格同样处理）。
3. `crates/nodes/src/renderer/animation.rs`：`intrinsic_size` 与顶点尺寸（来自帧像素尺寸）同样除以 pixelRatio。
4. `crates/nodes/src/nodes/sprite.rs` 的 `update_intrinsic_size`（九宫格目标尺寸路径）不涉及纹理像素，无需改动。

`AssetId` 仍以**逻辑 URL** 作为 key，从而保持"同一逻辑资源全局共享一个纹理、重复加载不重复试读"的性质。诊断日志里记录实际加载的 URL。

### 数据流

```
Core::new / resize_stage
  └─ 计算 T（surface 物理尺寸 / stage 尺寸）
     └─ 写入 moyu_resource 的全局 asset scale（AtomicU32 或 RwLock<f32>）

load_asset(AssetKind::Texture, "bg/room.png")
  └─ 逻辑 URL 作为 AssetId key（命中缓存则直接返回）
     └─ 异步任务 resolve_variant(src)：按候选顺序试读
        └─ 命中 → 字节 + 实际 URL + pixel_ratio
           └─ 解码上传纹理，写入 pixel_ratio
              └─ 节点轮询 TextureStatus::Ready（现有机制不变）
```

分辨率决策在**每次加载时采样当时的 T**：窗口缩放后新加载的资源会使用新档位，已加载的纹理保持不变（见下）。

## 配置

`index.json`（`MoyuConfig`，字段全部带默认值，新增字段不影响现有工程）：

| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `multiResAssets` | `"auto" \| "off" \| number` | `"off"` | `off`：完全关闭（等价于现在）；`auto`：按 T 在候选集合中匹配；数值：只使用该档位（不受候选集合约束），缺失时回退基础图。 |
| `multiResAssetScales` | `number[]` | `[1.5, 2]` | 除基础图外要尝试的变体档位。**整体覆盖**默认值，不做追加。空数组表示只使用基础图（零试读）。 |
| `multiResAssetPolicy` | `"quality" \| "balanced"` | `"quality"` | 候选集合内的排序策略。仅在 `multiResAssets` 为 `"auto"` 时有意义。 |

```json
{
  "stageSize": "1920x1080",
  "multiResAssets": "auto"
}
```

语义说明：

- **默认集合为什么是 `[1.5, 2]`**：覆盖常见的 1.5 倍屏与 2 倍（HiDPI / 4K）场景；集合越短，无变体项目的试读成本越低，因此默认不放 `3` / `4`，需要的项目显式声明。
- **默认为什么是 `off`**：试读在 web 上会变成额外的 HTTP 请求，而多倍图只对高分屏提升明显，不适合代所有项目付出这个代价。开启只需一行 `"multiResAssets": "auto"`。
- **`multiResAssets: 2`（强制档位）**：绕过候选集合与策略，只用 `abc@2x.png`，不存在则用基础图。用于 QA 对齐画质、以及未来"画质设置"的锚点。
- **覆盖而非追加**：`multiResAssetScales` 一旦写出就完全取代默认值；要保留默认行为只需不写该字段。
- **非法值**：`multiResAssets` 为正数以外的数字、或集合含非正数或 `1`（基础图已隐式包含）时，启动记 `warn!` 并回退到默认行为。

配置 schema 是外链 gist，改动后需要同步；`moyu-docs` 的 `customize/settings.md` 字段表与 `start/assets.mdx` 需要新增说明。

## 已知取舍与边界

- **候选集合外的高倍图会被静默忽略**：这是"无法列举目录"的直接结果。靠两道预检缓解（见下），编辑器也会在扫描 `assets/` 时给出警告。
- **试读开销与资源数成正比**（启用后，无变体项目在 `T > 1` 时每资源 ≤ 2 次失败读）。默认关闭即避开这一代价；已启用的项目如果后来不需要变体，把它改回 `"off"` 即可。
- **不热切换**：窗口尺寸变化后，已加载纹理保持原档位，只影响之后新加载的资源。原因是 `AssetId` 以 URL 为 key、渲染器按 `AssetId` 缓存 bind group，热替换需要遍历节点并失效缓存，收益（清晰度）与复杂度（卡顿、闪烁、多份显存）不匹配。未来如需"画质设置"，可以再加 `system` 命令显式刷新。
- **同一逻辑资源在会话内可能出现两种档位**（窗口缩放前后加载的实例）。这是不热切换的直接结果，只影响显存占用。
- **素材被节点放大或相机变焦**时，引擎只按舞台倍率选档：1280 宽背景铺满 1920 舞台的场合需要作者直接提供更大的基础图或对应变体。
- **与 mipmap 的关系**：两者独立，不做联动。`enableMipmaps` 是用户全局开关，多倍图只决定"加载哪个文件"，选中的文件照常走现有纹理加载路径（`load_image_to_texture` 会按该开关决定是否生成 mip 链），因此两个功能天然组合：用户开启时变体纹理也带 mip，未开启时都不带。
- **过采不会因本功能而变得更严重**：默认集合下过采比上限为 1.49（T 略大于 1 时选 `@1.5x`），与今天 720p 窗口显示 1080p 素材的过采比一致。只有自定义集合跨度较大（例如 `[1, 4]`）时才会超过双线性采样的舒适区，文档中提示这类情况开启 `enableMipmaps`。
- **包体**：变体会整体进入包内（`moyu pack` 只是复制 `assets/`，无需改动），安装包与下载体积相应变大。
- **编辑器**：变体文件不应出现在资源选择器中（FishFlow 的 `assets/` 扫描与 `x-asset-kind` 字段）。否则作者会直接引用 `abc@2x.png`，尺寸语义变化且机制失效。
- **内置资源与调试接口**：`insert_asset`（splash 的 logo/white）、`readFile`、调试桥均不做解析。

## 测试与验收

手工验证矩阵（引擎无单元测试，用 `yarn engine:web` / `engine:native` 观察）：

1. **无变体工程（默认配置）**：资源请求数与现在完全一致，不得出现任何 `@Nx` 请求。
2. **带变体工程**：`T = 2` 时使用 `@2x`，画面构图与使用基础图完全一致（尺寸补偿正确），无位置 / 尺寸偏移。
3. **候选集合**：`multiResAssetScales: []` 时零试读；集合含 `1.33` 时 `T = 1.33` 能命中 `@1.33x`；集合外的文件（存在 `@1.33x` 但未声明）确定不被使用且不报错。
4. **策略与开关**：`off` 与现在逐项一致；`T = 1.2` 时 `quality` 选 `@1.5x`，而 `balanced` 选基础图（`|ln(1/1.2)| = 0.18 < |ln(1.5/1.2)| = 0.22`）；强制值 `2` 在 `@2x` 缺失时落到基础图且不报错。
5. **平台**：desktop 缩放窗口、4K 全屏、Android 真机横屏（`T ≈ 1`，应始终用基础图）、web（含静态服务器把未知路径回退成 200 + HTML 的场景）。
6. **回归**：音频、视频、字体、`readFile`、内置资源不受影响。

## 被否决的方案

### 目录式变体（`assets@2x/…`）

按倍率分目录，启动时只需检查目录是否存在。优点是探测成本一次性、编辑器可直接忽略整个目录；缺点是目录结构需要平行维护、路径映射易错、与 iOS / Android / Web 的既有命名习惯不符。`@Nx` 后缀更符合行业惯例，且文件相邻便于美术管理。

### 构建期资源清单（manifest）

`pack` / dev server 生成变体清单，引擎直接查表，零探测。它解决了"无法列举目录"的根本问题，但引入构建步骤与陈旧风险（dev 下新增文件不生效），且需要覆盖 CLI、dev server、编辑器预览三处。列为后续优化：若将来 web 上的探测开销成为问题，可让引擎在 `assets/` 根下读取可选清单，缺失时回退到本文的探测策略。

### 只提供内置档位、不可配置

如果候选档位写死在引擎里，就无法表达"我确实要 `@1.33x`"，也不能让不希望使用多倍图的 web 项目把试读成本压到零。配置化同时解决了这两个问题，且没有引入构建步骤。

### 跨资源的"跳过"缓存

早期设计允许"某档位在任何资源上都没成功过就全局跳过"，把无变体项目的成本压到"仅首个资源付费"。但单个资源是否有多倍图是独立事实，全局跳过会漏检（同一项目里背景有 `@2x`、UI 素材没有是常见情况）。改为只做按资源的缓存，并把"尝试哪些档位"交给配置，行为与成本都变得可预测。

### 在 JS / kit 层实现

由 kit 根据 `getStageSize()` 与 `getWindowInnerSize()` 计算倍率并改写 `src` 字符串。不改 Rust 即可落地，但会污染存档与 `gameState` 中的路径、影响所有 `src` 落点（含剧本数据），并且与引擎内部的像素倍率补偿无法配合。多倍图是引擎级资源语义，应下沉到 Rust。

### 运行时热切换档位

见"已知取舍"，复杂度与风险不匹配收益，v1 不做。

### 默认开启

先前的方案默认开启，理由是"关闭会让功能不可用（作者不会主动开）"。但试读在 web 上会转化为额外的 HTTP 请求，而多倍图只对高分屏有可见收益，让所有项目默认付出这个代价并不合适。改为默认关闭后，代价变成"需要作者主动开启"，而文档与 `index.json` 的字段说明已经把开启方式写在显眼位置。

## 预检

变体文件不被使用（或配置指向了不存在的档位）时引擎不会报错，这是本功能最容易踩的坑。CLI 与编辑器各做一道预检。

**CLI 预检**（`packages/cli/src/utils/multi-res-assets.ts`，由 `moyu run` / `moyu pack` 在启动前调用；扫描 `assets/` 与 `index.json`，只警告不阻断）：

1. 存在 `@Nx` 文件但 `multiResAssets` 为 `off`（含未设置）→ 警告文件数量，并提示改为 `"auto"`。
2. 存在 `@Nx` 文件但该档位不在候选集合中（或与 `Fixed` 值不符）→ 按档位分组警告，附一个示例文件。
3. 存在 `@1x` 文件 → 警告：档位 `1` 由基础图承担，该文件永远不会被使用。
4. 候选集合里的档位在 `assets/` 中一个文件都没有 → 提示"每个资源会多一次失败试读"。
5. 存在 `abc@2x.png` 但缺少基础图 `abc.png` → 列出这些变体，说明无法被引用。

编辑器侧（FishFlow）的计划：扫描时识别变体文件并从资源选择器中隐藏，同时给出与 CLI 一致的警告。

### 实施备注

- **按资源缓存未单独实现**：`ResourceManager::load_asset` 已按逻辑 URL 缓存整个 asset，重复加载会提前返回，不会重复试读。
- **`read_asset`**：动画节点不经 `ResourceManager`（它自带解码与纹理管理），因此 `moyu_resource` 额外导出 `read_asset(src)`，供这类调用方复用同一套档位规则。
- **验证方式**：用调试桥（`moyu mcp` / `moyu debug`）驱动引擎，覆盖 6 种配置；尺寸补偿以加载 `@1.5x` 后节点的 `intrinsicSize` 与基础图场景一致为准。实施过程中由此发现并修复两个缺陷（变体路径漏写 `x`、固定档位被 `dedupe` 排到基础图之后）。

## 结论

多倍图适配可以在**不改变现有项目行为**的前提下引入：默认关闭，开启后按物理像素与舞台尺寸推导的倍率选档，候选档位由配置给出（带内置默认值），匹配默认清晰度优先。

最关键的约束是引擎没有目录列举能力，因此"要试哪些档位"必须已知；把它做成配置项而不是隐藏的内置梯度，既让 `@1.33x` 这类档位可用，也让不需要多倍图的项目能把成本压到零。`T ≤ 1` 时基础图是第一个候选，零试读，与现在完全一致。

改动集中在 `moyu_resource`（解析、试读、缓存）与 `moyu_core` / `moyu_nodes`（倍率传递与尺寸补偿），跨仓影响集中在编辑器（隐藏变体文件、警告未声明档位）与文档。
